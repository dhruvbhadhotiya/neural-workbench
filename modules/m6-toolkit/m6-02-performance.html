AMP, gradient accumulation and DDP

— · Lesson 2 of 7 · Exact math labs

Throughput is a design constraint: decide what fits in memory, emulate batches you cannot fit, and average gradients across workers without changing the optimisation problem.

Objectives

  • Estimate activation memory from shapes and dtype, then check it against a budget.
  • Use gradient accumulation to reach an effective batch of \(B\cdot A\cdot W\).
  • Explain loss scaling with a concrete underflow example.
  • Derive the all-reduce mean used by DistributedDataParallel.

You know this from ML → here it becomes

In classical ML, a bigger dataset just meant longer runtime. Here the batch size, dtype and number of GPUs form a triangle: push one side and the others change. "Train longer" is no longer a free answer — memory and arithmetic decide which experiments are even possible.

Intuition: three knobs, one budget

A forward pass must keep the activation of every layer until the backward pass arrives. That live set grows linearly with batch size \(N\), with each feature map's channel count \(C\), and with spatial area \(H'W'\). Using fp16 instead of fp32 halves those bytes. Gradient accumulation lets you pretend the batch is larger by summing gradients over \(A\) micro-batches before one optimizer step; multiple workers \(W\) add a third factor.

The trap is that they are not interchangeable. Batch normalization computes statistics over the micro-batch on each rank, so shrinking the micro-batch while raising \(A\) changes what the layer sees. AMP's reduced precision needs loss scaling because small gradients underflow to zero in fp16. DDP must average gradients, not sum them, or the larger \(W\) would silently multiply the learning rate.

Memory depends on what you store (activations, parameters, optimizer state); optimisation depends on what you accumulate before stepping. Confusing the two is why "just add GPUs" often fails.

The math

1 · Activation memory

For a stack of layers whose live outputs have shapes \((C_l,H_l,W_l)\), with batch \(N\) and \(b\) bytes per scalar, the activation memory is

\[ M_{\text{act}} = N\,b\sum_l C_l H_l W_l \]

Here \(N\) is the micro-batch size per device, \(b\) is 4 for fp32 and 2 for fp16/bf16, \(C_l,H_l,W_l\) are the channel count and spatial size of live feature map \(l\). Scaling by 2 for activations that a backward pass must retain is a common conservative adjustment; the formula above counts one copy per live map.

Worked example. A small CNN holds two feature maps per sample: \((64,32,32)\) and \((128,16,16)\). Their sizes are \(64\cdot32\cdot32=65{,}536\) and \(128\cdot16\cdot16=32{,}768\), summing to \(98{,}304\) scalars. With \(N=8\) and fp16 (\(b=2\)): \(M=8\cdot2\cdot98{,}304=1{,}572{,}864\) bytes \(=1.5\) MiB. In fp32 that doubles to \(3{,}145{,}728\) bytes \(=3.0\) MiB.

2 · Effective batch

\[ B_{\text{eff}} = B\cdot A\cdot W \]

\(B\) is the per-device micro-batch, \(A\) the number of accumulation steps between optimizer updates, and \(W\) the number of workers. Each micro-batch is divided by \(A\) in the loss so that the accumulated gradient matches one large batch.

Worked example. With \(B=8\), \(A=4\), \(W=2\): \(B_{\text{eff}}=8\cdot4\cdot2=64\) examples per optimizer step. If each micro-batch loss is the mean over its 8 examples, the accumulated gradient is \(\sum_{a=1}^{4}\nabla \mathcal{L}_a/4\), the mean over the 32 examples visible to one worker; DDP then averages across the 2 workers, recovering the gradient of the 64-example batch.

3 · AMP loss scaling

\[ \tilde{\mathcal{L}} = S\,\mathcal{L}, \qquad \nabla\theta = \frac{1}{S}\nabla\!\left(S\mathcal{L}\right) \]

\(S\) is the loss scale (a power of two in typical implementations), \(\mathcal{L}\) the unscaled loss and \(\nabla\theta\) the gradient actually applied. The forward pass and loss are usually computed in fp32; selected ops run in fp16 under an autocast context. Gradients in fp16 have a smallest normal value near \(6\times10^{-5}\), so anything smaller becomes zero.

Worked example. Suppose a true gradient is \(g=1\times10^{-8}\) and \(S=256\). The scaled gradient is \(256\times10^{-8}=2.56\times10^{-6}\), still below the fp16 normal threshold but inside the subnormal range; with \(S=65{,}536\), \(gS=6.55\times10^{-4}\), safely representable. After unscaling, \((6.55\times10^{-4})/65{,}536=1.0\times10^{-8}\) — the same number the fp32 path would have produced. Conversely, if \(g=100\) and \(S=65{,}536\), \(gS=6.55\times10^{6}\) exceeds fp16's maximum \(65{,}504\); the scaler detects the inf, skips the step, and halves \(S\).

4 · DDP all-reduce mean

\[ \bar g = \frac{1}{W}\sum_{w=1}^{W} g_w \]

\(g_w\) is the gradient computed on worker \(w\) from its own \(B\cdot A\) examples, and \(\bar g\) is the gradient every worker uses for its identical parameter update. DDP overlaps this all-reduce with backward computation by bucketizing gradients.

Worked example. Four workers produce one parameter's gradient fragments \(g=(0.4,\;0.8,\;-0.2,\;1.0)\). Their sum is \(2.0\), so the mean is \(2.0/4=0.5\). Each worker applies \(\theta\leftarrow\theta-\eta\cdot0.5\); with \(\eta=0.1\), the parameter moves by \(0.05\) on every worker, keeping replicas identical. A sum-reduce of \(2.0\) would make the step four times too large.

A useful mental check: doubling \(B\) doubles activation memory but halves the number of optimizer steps per epoch in wall-clock terms only if throughput scales. Doubling \(A\) keeps memory roughly flat while doubling the work before a step. Doubling \(W\) doubles aggregate throughput but leaves each replica's memory unchanged.

Code: autocast, scaler, accumulation and DDP

import torch
from torch import nn
from torch.nn.parallel import DistributedDataParallel as DDP

# ---- AMP + gradient accumulation on one GPU -------------------------------
model = nn.Sequential(nn.Conv2d(3, 64, 3, padding=1), nn.ReLU(),
                      nn.AdaptiveAvgPool2d(1), nn.Flatten(), nn.Linear(64, 10)).cuda()
opt = torch.optim.SGD(model.parameters(), lr=0.1)
scaler = torch.amp.GradScaler("cuda", init_scale=65536.0)
B, ACCUM = 8, 4                      # B_eff = 8 * 4 = 32 on one worker

opt.zero_grad(set_to_none=True)
for step, (x, y) in enumerate(loader):
    x, y = x.cuda(non_blocking=True), y.cuda(non_blocking=True)
    with torch.amp.autocast("cuda", dtype=torch.float16):
        out = model(x)                # selected ops run in fp16
        loss = nn.functional.cross_entropy(out, y) / ACCUM
    scaler.scale(loss).backward()     # gradients are scaled, not the parameters
    if (step + 1) % ACCUM == 0:
        scaler.unscale_(opt)          # REQUIRED before clipping
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(opt)              # skips the step if grads are inf/NaN
        scaler.update()               # grows/shrinks the scale
        opt.zero_grad(set_to_none=True)

# ---- DDP skeleton (launch with torchrun --nproc_per_node=2 train.py) ------
import os, torch.distributed as dist
dist.init_process_group("nccl")
rank, world = dist.get_rank(), dist.get_world_size()
torch.cuda.set_device(rank)
model = DDP(model.cuda(rank), device_ids=[rank])
# DDP averages gradients over `world` ranks automatically: g_bar = mean(g_w).
# Keep B the same per rank: B_eff = B * ACCUM * world.
# For BatchNorm with tiny per-rank B, use SyncBatchNorm.convert_sync_batchnorm(model).
dist.destroy_process_group()

bf16 keeps fp32's exponent range, so many bf16 workflows do not need loss scaling; fp16 has the same mantissa width but a much narrower exponent range and does. Check device support before choosing: scaling is harmless with bf16 but unnecessary overhead.

Common mistakes

optimizer.step() inside the loop

Calling the optimizer on every micro-batch turns \(A=4\) into four small steps instead of one large step. Step only at the accumulation boundary, after dividing the loss by \(A\).

Clipping before unscaling

Gradient norms are multiplied by the loss scale. Clip after scaler.unscale_(opt), or the threshold effectively becomes \(S\) times smaller than you intended.

Missing GradScaler with fp16

Without scaling, small fp16 gradients underflow to zero and the loss becomes NaN or plateaus. The NaN-only-with-AMP symptom points here first.

BatchNorm with tiny per-GPU batches

Each rank sees only its micro-batch, so \(B=1\) makes BN statistics noisy. Use SyncBatchNorm or GroupNorm, or raise \(B\) and lower \(A\) within the memory budget.

Debug this

The loss is finite in fp32 but becomes NaN as soon as autocast is enabled. The code uses autocast, scales the loss manually by 65536, and calls loss.backward() followed by optimizer.step(). What is missing?

Show the likely cause and the fix

There is no GradScaler. Scaling the loss by hand without unscaling and without overflow detection leaves scaled gradients in the parameters and can produce infinities. Use scaler.scale(loss).backward(), scaler.unscale_(optimizer) before clipping, scaler.step(optimizer) and then scaler.update(). If your device supports bf16 well, autocast(dtype=torch.bfloat16) without a scaler is the simpler alternative.

Second suspect: a loss computed in fp16 (for example a squared difference before the final cast). Keep reduction ops such as cross-entropy in fp32 even under autocast.

Summary

1 · Activation memory is \(N b\sum_l C_lH_lW_l\): for two maps at \(N=8\), fp16 costs 1.5 MiB and fp32 costs 3.0 MiB.
2 · Effective batch \(B\cdot A\cdot W=8\cdot4\cdot2=64\); divide the loss by \(A\) and let DDP average over \(W\).
3 · Loss scaling multiplies by \(S\) before backward and divides by \(S\) after; unscale before clipping or NaN follows.

Cheat sheet — M6·02

  • \(M_{\text{act}}=Nb\sum C_lH_lW_l\); fp32 \(b=4\), fp16/bf16 \(b=2\).
  • \(B_{\text{eff}}=B\cdot A\cdot W\); loss divided by \(A\), step at the boundary.
  • \(\tilde{\mathcal L}=S\mathcal L\); unscale by \(S\) before clipping; skip step on inf.
  • DDP: \(\bar g=\frac1W\sum_w g_w\); NCCL all-reduce, one process per GPU.
  • fp16 needs a scaler; bf16 usually does not. BN + tiny \(B\) → SyncBatchNorm.
