Seeds, determinism and experiment tracking

— · Lesson 1 of 7 · Illustrative spread + Exact checklist labs

A single seed is not an experiment. Learn which sources of randomness a deep-learning run has, how to pin them down, and how to report a metric whose uncertainty you can actually compute.

Objectives

  • Name the independent RNG sources in a PyTorch run and seed each one.
  • Explain why deterministic kernels cost throughput and what to log besides the seed.
  • Compute the standard error of a metric and average results over seeds correctly.
  • Verify a replay of the same configuration bit-for-bit using a config hash.

You know this from ML → here it becomes

In scikit-learn, random_state=42 on the estimator was usually enough. A deep run has at least four independent random streams — Python, NumPy, the CPU/CUDA torch generators and the DataLoader workers — plus algorithm choices that are nondeterministic even with a fixed stream. Reproducibility is now a system property, not a keyword argument.

Intuition: four streams, plus a fifth source

Think of a run as a recipe that draws random numbers at five different stations. Station one is Python's random, used by dataset splits and augmentation libraries. Station two is NumPy's legacy global generator, still used by many data pipelines. Station three is PyTorch's CPU generator (weight init, dropout). Station four is the CUDA generator, used by GPU-only sampling such as dropout masks on device. Station five is not an RNG at all: a GPU kernel that reduces in a different order on different launches, such as atomic additions in a scatter or a convolution selected by cuDNN's autotuner.

Seeding only torch.manual_seed fixes station three. If your augmentation uses NumPy, or your loader has four worker processes, each worker inherits a different — often uncontrolled — state, and the training examples arrive in a different order. The loss curve then differs by a few percent between two "identical" runs, which is exactly the symptom in the debug challenge at the end of this lesson.

Repeatability needs a fixed seed and a fixed execution path: same data order, same kernel algorithms, same library versions, same hardware class. A seed without a config hash is a number nobody can interpret later.

The math: spread, standard error and seed averaging

1 · Variance of one metric estimate

Let \(A\) be the accuracy on a test set of \(n\) examples drawn from a population with true accuracy \(p\). Each example is a Bernoulli trial, so \(\operatorname{Var}(A)=p(1-p)/n\). Here \(p\) is the true accuracy of the model on the population and \(n\) is the number of test examples — not the number of seeds.

\[ \widehat{\operatorname{Var}}(A)=\frac{\hat p(1-\hat p)}{n}, \qquad \operatorname{SE}(A)=\sqrt{\frac{\hat p(1-\hat p)}{n}} \]

Worked example. A model gets \(84\) of \(100\) test items right, so \(\hat p=0.84\). Then \(\hat p(1-\hat p)=0.84\cdot0.16=0.1344\), and \(\widehat{\operatorname{Var}}=0.1344/100=0.001344\). The standard error is \(\sqrt{0.001344}=0.0367\): the usual 95% interval is roughly \(0.84\pm1.96\cdot0.0367\), i.e. \([0.768,\;0.912]\). This interval is about the test sample; seed variability is a separate quantity measured next.

2 · Across-seed variance

Let \(a_1,\dots,a_S\) be the final metric from \(S\) independently seeded runs, with sample standard deviation \(s_a=\sqrt{\frac{1}{S-1}\sum_{s=1}^{S}(a_s-\bar a)^2}\). The mean over seeds is

\[ \bar a=\frac{1}{S}\sum_{s=1}^{S} a_s, \qquad \operatorname{SE}(\bar a)=\frac{s_a}{\sqrt{S}} \]

Here \(S\) is the number of seeds and \(a_s\) is the metric of run \(s\). Dividing by \(\sqrt{S}\) is the whole point: four seeds cut the seed-related standard error in half, but they do not shrink the test-set error above.

Worked example. Three seeds give \(0.82,\;0.85,\;0.87\). Then \(\bar a=(0.82+0.85+0.87)/3=2.54/3=0.8467\). Deviations from the mean are \(-0.0267, 0.0033, 0.0233\); their squares sum to \(0.000711+0.000011+0.000544=0.001266\); with \(S-1=2\) we get \(s_a=\sqrt{0.000633}=0.0252\) and \(\operatorname{SE}(\bar a)=0.0252/\sqrt3 =0.0145\). Reporting "\(0.847\pm0.015\) (3 seeds)" is honest; reporting only \(0.87\) is cherry-picking the best seed.

3 · Config hashing

A config hash is a fixed-size fingerprint of every setting that could change the result. With a 32-bit FNV-1a hash \(h(c)\), the probability that two different configs collide is about \(1/2^{32}\approx2.3\times10^{-10}\) for one pair.

Worked example. Two configs differ only in the seed field. Hashing the canonical JSON strings {"seed":1,"lr":0.01} and {"seed":2,"lr":0.01} gives two different 32-bit values; the widget below prints them as eight hex digits. Canonical means sorted keys and fixed number formatting, or the same config can hash differently just because a dictionary was iterated in another order. A checkpoint should carry this hash, the library versions, the git commit and the seed — weights alone do not tell you which recipe produced them.

Read the replay digest before trusting the spread: if two runs with the same seed and the same config produce different digests in the simulator, no amount of seed averaging will rescue the experiment. On real GPUs, set torch.backends.cudnn.benchmark = False and call torch.use_deterministic_algorithms(True); some operations will then raise an error instead of silently choosing a fast, nondeterministic algorithm. That error is useful — it tells you which kernel to replace.

Code: seeding, deterministic kernels and a minimal logger

import os, random, json, hashlib
import numpy as np
import torch
from torch.utils.data import DataLoader

SEED = 42
os.environ["PYTHONHASHSEED"] = str(SEED)   # set before Python starts
random.seed(SEED)
np.random.seed(SEED)
torch.manual_seed(SEED)
torch.cuda.manual_seed_all(SEED)
torch.backends.cudnn.benchmark = False     # no autotuner kernel switching
torch.backends.cudnn.deterministic = True
torch.use_deterministic_algorithms(True)   # raise on nondeterministic ops

def seed_worker(worker_id):
    wseed = torch.initial_seed() % 2**32
    random.seed(wseed); np.random.seed(wseed)

g = torch.Generator(); g.manual_seed(SEED)
loader = DataLoader(dataset, batch_size=32, shuffle=True,
                    num_workers=4, worker_init_fn=seed_worker, generator=g)
# All four worker streams are now distinct but reproducible.

def canonical(cfg):
    return json.dumps(cfg, sort_keys=True, separators=(",", ":"))

cfg = {"seed": SEED, "lr": 1e-3, "epochs": 10, "arch": "mlp-256"}
cfg_hash = hashlib.sha256(canonical(cfg).encode()).hexdigest()[:16]

record = {"cfg": cfg, "cfg_hash": cfg_hash, "seed": SEED,
          "torch": torch.__version__, "cuda": torch.version.cuda,
          "final_acc": 0.0}
with open("run.jsonl", "a") as f:
    f.write(json.dumps(record) + "\n")

# For multiple seeds: train once per seed, then report mean and sample std.
accs = []
for s in (0, 1, 2, 3, 4):
    torch.manual_seed(s)                  # re-seed before each run
    accs.append(train_one_run(s))         # your training function
mean_acc = float(np.mean(accs))
se_acc = float(np.std(accs, ddof=1) / np.sqrt(len(accs)))
print(f"{mean_acc:.4f} +/- {se_acc:.4f} over {len(accs)} seeds, cfg {cfg_hash}")

Use CUBLAS_WORKSPACE_CONFIG=:4096:8 in the environment when deterministic CUDA matmuls are required; without it some CUDA versions raise at use_deterministic_algorithms(True). Determinism can reduce throughput, so many teams run deterministic verification builds and faster production builds from the same config.

Common mistakes

Seeding only torch

Python, NumPy and DataLoader workers keep their own streams. A fixed torch.manual_seed still leaves augmentation order and worker behaviour random.

Benchmark mode left on

cudnn.benchmark=True picks a kernel based on timing. The pick can change between machines or runs, so bitwise replay fails even with every seed fixed.

Comparing runs with different order

Changing num_workers or batch size changes the sequence of examples. The seed is identical but the optimisation trajectory is not — log these knobs with the seed.

Reporting the best of five seeds

Taking the maximum of \(S\) noisy metrics biases the estimate upward. Report the mean and \(s_a/\sqrt S\), and state \(S\) next to the number.

Debug this

Two runs use the same seed, the same code and the same GPU, yet final accuracy differs by about 3%. The training loop, model and loss are identical. What do you check first?

Show the likely cause and the fix

The DataLoader workers. Each worker process inherits or derives its own NumPy/Python RNG; if worker_init_fn is missing (or uses the same seed for every worker), random augmentation and shuffle order differ between runs. Pass a seeded generator to the loader and a seed_worker function that reseeds from torch.initial_seed(). Also set shuffle=True through that generator rather than a global NumPy state.

If the difference survives on one worker, the next suspect is cudnn.benchmark or a nondeterministic scatter/atomic kernel. Turn on torch.use_deterministic_algorithms(True) and follow the exception it raises.

Check yourself

Summary

1 · Seed Python, NumPy, torch CPU, torch CUDA and every DataLoader worker — then disable cuDNN autotuning.
2 · A config hash, library versions and the seed belong in every checkpoint; without them the number has no context.
3 · Report \(\bar a \pm s_a/\sqrt S\) over several seeds; test-set error \(p(1-p)/n\) is a separate quantity.

Cheat sheet — M6·01

  • Seeds: random, np.random, torch.manual_seed, torch.cuda.manual_seed_all, worker generator.
  • Test error: \(\operatorname{SE}=\sqrt{\hat p(1-\hat p)/n}\); with \(n=400,\hat p=0.75\): 0.0217.
  • Seed error: \(\operatorname{SE}(\bar a)=s_a/\sqrt S\); \(S=4\) halves it.
  • Determinism: cudnn.benchmark=False, use_deterministic_algorithms(True), fixed data order.
  • Log: seed, canonical config hash, versions, hardware class, commit, metric.
