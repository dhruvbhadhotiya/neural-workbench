Hugging Face, LoRA and model decisions

— · Lesson 5 of 5 · Exact math labs

The pretrained ecosystem hands you a checkpoint and a tokenizer. Your job is to adapt it cheaply, count what you are training, and pick an architecture that matches the task.

Objectives

  • Run a Hugging Face pipeline and describe what the checkpoint and tokenizer each provide.
  • Derive the LoRA update \(W'=W+BA\) and count its trainable parameters as \(r(d+k)\).
  • Work the \(d=k=768,\ r=8\) case by hand and compare it with full fine-tuning.
  • Choose an encoder, decoder or encoder–decoder model from the task's input and output shape.

You know this from ML → here it becomes

In scikit-learn you called fit and predict on one object. Here a checkpoint supplies pretrained weights, a tokenizer supplies the exact id mapping those weights expect, and a head maps hidden states to your labels. Instead of updating every weight, LoRA freezes the checkpoint and trains two small matrices per targeted layer.

Intuition: adapt a small subspace

Full fine-tuning updates every entry of a weight matrix \(\mathbf W\in\mathbb R^{d\times k}\): \(dk\) parameters (plus \(k\) biases). LoRA keeps \(\mathbf W\) frozen and learns an update \(\Delta\mathbf W=\mathbf B\mathbf A\) with \(\mathbf B\in\mathbb R^{d\times r}\) and \(\mathbf A\in\mathbb R^{r\times k}\). If \(r\ll\min(d,k)\), the update lives in a low-rank subspace and costs only \(dr+rk=r(d+k)\) trainable numbers. Symbols: \(d\) is the output dimension of the layer, \(k\) its input dimension, \(r\) the LoRA rank, and \(\alpha\) a scaling constant.

Architecture choice follows the shape of the task. An encoder reads a whole input and is natural for classification or token tagging. A decoder generates a sequence one token at a time and is natural for open-ended text. An encoder–decoder maps one sequence to another, as in translation or summarisation. These are design patterns, not performance claims.

LoRA trains a rank-\(r\) correction instead of the full matrix. The saving is arithmetic: \(r(d+k)\) versus \(dk+k\). At \(d=k=768, r=8\) that is 12,288 rather than 590,592 numbers per layer — about 2.08%.

The math

1 · The low-rank update

With \(\mathbf W\) frozen, the layer computes

\[ \mathbf h=\mathbf W\mathbf x+\frac{\alpha}{r}\,\mathbf B\mathbf A\mathbf x, \qquad \mathbf B\in\mathbb R^{d\times r},\ \mathbf A\in\mathbb R^{r\times k},\ \Delta\mathbf W=\mathbf B\mathbf A \]

\(\operatorname{rank}(\mathbf B\mathbf A)\le r\): a product with an inner dimension \(r\) cannot have higher rank. \(\alpha/r\) is a fixed scale chosen when the adapter is configured; it is not learned. \(\mathbf A\) is typically initialised randomly and \(\mathbf B\) with zeros, so training starts exactly at the pretrained model.

Worked example. Take \(d=3,k=2,r=1\), \(\mathbf A=\begin{bmatrix}1&2\end{bmatrix}\), \(\mathbf B=\begin{bmatrix}3\\4\\5\end{bmatrix}\), and a toy \(\mathbf W=0\). Then \(\mathbf B\mathbf A=\begin{bmatrix}3&6\\4&8\\5&10\end{bmatrix}\) (rank 1: row 2 is \(\tfrac43\) of row 1). For \(\mathbf x=(1,1)^\top\), \(\mathbf B\mathbf A\mathbf x=(3+6,4+8,5+10)^\top=(9,12,15)^\top\). With \(\alpha=r\), the scale is 1 so the answer is unchanged.

2 · Trainable parameter count

\(\mathbf B\) has \(d\times r\) entries and \(\mathbf A\) has \(r\times k\) entries, so the adapter has \(dr+rk=r(d+k)\) trainable parameters. Full fine-tuning of the same linear layer takes \(dk+k\) (weights plus a bias). The fraction trained is \(r(d+k)/(dk+k)\), and the reduction factor is \((dk+k)/(r(d+k))\).

Worked example — \(d=k=768,\ r=8\), by hand. First, \(d+k=768+768=1536\). Multiply by the rank: \(r(d+k)=8\times1536=12{,}288\) trainable parameters for one adapter. Full fine-tuning of that layer needs \(dk+k=768\times768+768=589{,}824+768=590{,}592\) parameters. The fraction is \(12{,}288/590{,}592=0.020806\approx2.08\%\), i.e. roughly 48× fewer trainable numbers (exactly 48.0625× from the same division). This is arithmetic on a synthetic layer, not a count for any released checkpoint.

3 · Rank and scaling

The rank \(r\) is a budget knob: larger \(r\) increases capacity and trainable count linearly. The scale \(\alpha/r\) keeps the update's magnitude roughly stable as \(r\) changes. If you double \(r\) and keep \(\alpha\) fixed, the number of trainable parameters roughly doubles while each update is halved before scaling.

Worked example. With \(\alpha=16\), \(r=8\) gives \(\alpha/r=2\). Doubling to \(r=16\) yields \(\alpha/r=1\) and \(16(768+768)=24{,}576\) trainable parameters — exactly twice the 12,288 from the \(r=8\) case. If \(\alpha\) were also doubled to 32, the scale would return to 2.

4 · Adapter total across modules

If \(m\) layers are targeted, multiply both counts by \(m\): \(N_{\text{LoRA}}=m\,r(d+k)\) and \(N_{\text{full}}=m(dk+k)\). Only the percentages stay the same across \(m\) when all modules share a shape.

Worked example. For a synthetic profile with \(m=12\) identical \(d=k=768\) layers and \(r=8\), the adapter trains \(12\times12{,}288=147{,}456\) parameters, while full fine-tuning would train \(12\times590{,}592=7{,}087{,}104\). Their ratio is still 48.0625×. The lab's other profiles repeat the same arithmetic with different synthetic shapes; none of them is a published model size.

Code

First the pretrained workflow in PyTorch: a pipeline for a quick check, then PEFT's LoraConfig and get_peft_model with a printed trainable-parameter count. The second listing shows how to target specific modules and merge the adapter at export. No checkpoint is downloaded at build time — run these in Colab with your own model id. Shapes are \((N,T)\) token ids and \((N,C)\) logits; for image checkpoints the convention is NCHW. 

from transformers import pipeline, AutoTokenizer, AutoModelForSequenceClassification
from peft import LoraConfig, get_peft_model, TaskType
import torch

# 1) Quick pretrained check (choose a checkpoint before running).
clf = pipeline("sentiment-analysis", model="distilbert-base-uncased-finetuned-sst-2-english")
print(clf("This lesson is clear."))          # list of {"label": ..., "score": ...}

# 2) Adapt a checkpoint to your own 2-class task.
name = "distilbert-base-uncased"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForSequenceClassification.from_pretrained(name, num_labels=2)
# input_ids: (N, T); attention_mask: (N, T); logits: (N, C=2)

config = LoraConfig(
    task_type=TaskType.SEQ_CLS,
    r=8,                 # rank: the 12,288-per-module case for d=k=768
    lora_alpha=16,       # alpha/r = 2
    lora_dropout=0.05,
    target_modules=["q_lin", "v_lin"],   # names depend on the checkpoint
)
model = get_peft_model(model, config)
model.print_trainable_params()             # exact printed count for your checkpoint

batch = tok(["first sentence", "second sentence"], padding=True,
            truncation=True, return_tensors="pt")
with torch.no_grad():
    logits = model(**batch).logits          # (N=2, C=2), pre-softmax
print(tuple(logits.shape))
from peft import LoraConfig, get_peft_model, TaskType

# Target modules must be the linear projections inside attention/FFN blocks.
cfg = LoraConfig(task_type=TaskType.SEQ_CLS, r=8, lora_alpha=16,
                 target_modules=["query", "value"])   # example names

peft_model = get_peft_model(base_model, cfg)
for n, p in peft_model.named_parameters():
    if p.requires_grad:
        pass                    # only A and B matrices appear here

n_train = sum(p.numel() for p in peft_model.parameters() if p.requires_grad)
n_total = sum(p.numel() for p in peft_model.parameters())
print("trainable", n_train, "total", n_total,
      "percent", round(100 * n_train / n_total, 4))

# Export: merge the adapter into the base weights before deployment.
merged = peft_model.merge_and_unload()
merged.save_pretrained("./merged")          # no adapter needed at inference
tok.save_pretrained("./merged")             # keep the matching tokenizer
# Note: generation also needs model.config.pad_token_id set correctly.

The counts printed by print_trainable_params() come from the actual checkpoint you load; our worked 12,288 is peradapter arithmetic at \(d=k=768, r=8\) on a synthetic layer. LoRA is not automatically better than full fine-tuning on every task — it is a budget and deployment trade-off that you should measure on your own validation set.

Common mistakes

Wrong padding side for generation

Encoder models usually pad on the right; decoder-only generation usually needs left padding so the final token of every sequence sits at the same index. A wrong tokenizer.padding_side makes batched generation misalign its predictions.

Missing pad_token_id

If the tokenizer has no pad token, set it explicitly (often to the EOS token) and make sure model.config.pad_token_id matches. Otherwise generation can sample the pad id or warn on every batch.

LoRA on the wrong modules

Parameter names differ across checkpoints (q_lin, query, …). A target_modules list that matches nothing trains zero parameters and silently leaves the model unchanged. Print the trainable count after wrapping.

Adapter not merged at export

Serving code that loads only the base checkpoint ignores an unmerged adapter. Either ship the adapter with the PEFT loader or call merge_and_unload() and save both the merged weights and the matching tokenizer.

Debug this

A reader reports: “LoRA training runs but the loss stays flat and the trainable count prints 0.” The configuration looks reasonable except for one line: 

cfg = LoraConfig(task_type=TaskType.SEQ_CLS, r=8, lora_alpha=16,
                 target_modules=["q_proj"])   # BUG: this checkpoint calls it "query"
model = get_peft_model(model, cfg)
model.print_trainable_params()               # prints 0
Show the likely cause and the fix

A parameter name that does not exist in the checkpoint selects no modules, so no \(A\) or \(B\) matrices are created and nothing can learn. Inspect the real names with [n for n, _ in model.named_modules()], choose the exact attention projections, and print the trainable count again. A related bug is freezing the wrong tensors: requires_grad=True must hold for the adapter parameters. If the count is small but nonzero and the loss is still flat, check that the head is also trainable and that the learning rate is not far too small.

Quick detector: after wrapping, assert any(p.requires_grad for p in model.parameters()) and record print_trainable_params() in the training log before the first step.

Summary

1 · A pretrained checkpoint supplies weights and config; a matching tokenizer supplies ids and masks, and a small head turns hidden states into task predictions.
2 · LoRA freezes \(\mathbf W\) and trains \(\mathbf B\mathbf A\): with \(d=k=768,r=8\), \(r(d+k)=8(768+768)=12{,}288\) parameters versus \(dk+k=590{,}592\) for full fine-tuning — about 2.08%.
3 · Match the architecture to the task shape, set padding and pad ids correctly, target real module names, and merge the adapter before export.

Cheat sheet — M4·05

  • \(W'=W+\frac{\alpha}{r}BA\), \(B\in\mathbb R^{d\times r}\), \(A\in\mathbb R^{r\times k}\); rank(BA) ≤ r.
  • Trainable count \(r(d+k)\). Worked: d=k=768, r=8 → 8×1536 = 12,288.
  • Full layer count \(dk+k\) = 589,824 + 768 = 590,592; 12,288/590,592 ≈ 2.08% (≈48× fewer).
  • With m targeted modules, multiply both counts by m; percentages are unchanged for identical shapes.
  • Scale α/r: α=16, r=8 → 2; α=16, r=16 → 1 with 24,576 trainable parameters.
  • Checks: matching target_modules, nonzero trainable count, left padding for generation, merged adapter at export.
